# 前后端数据协同规范 (Frontend-Backend Coordination)

本文档定义了政务数据平台的数据分类标准及协同规则，旨在解决爬虫数据源与前端展示分类不一致的问题。

## 1. 核心问题背景

*   **现状**: 爬虫脚本抓取的数据分类名称不统一（如 "人事信息"），且包含多种业务含义（既有招聘也有任免）。
*   **目标**: 前端需要清晰的业务分类（"人事任免", "招考招聘"），且不能展示为空。
*   **解决方案**: 后端在数据同步阶段执行**自动映射**，将爬虫的原始分类转换为标准业务分类。

## 2. 数据分类标准 (Category Standards)

前端在调用接口时，应严格使用以下标准分类标签（Category Tag）。

| 标准分类名称 (Tag) | 编码 (Code) | 说明 |
| :--- | :--- | :--- |
| **人事任免** | 1002 | 涉及干部任免、职务变动等信息 |
| **招考招聘** | 1003 | 涉及公务员考试、遴选、面试、成绩等信息 |
| **政策法规** | 1001 | 政策文件、法律法规 (预留) |
| **规划计划** | 1004 | 发展规划、年度计划 (预留) |
| **统计数据** | 1005 | 经济指标、统计公报 (预留) |

> **注意**: 前端可通过接口 `GET /api/public-info/category/list` 动态获取上述列表。

## 3. 后端自动映射逻辑 (Mapping Logic)

为了适配爬虫数据，后端在同步数据（Redis -> MySQL）时会执行以下规则：

### 3.1 人事信息拆分规则
当爬虫提供 `category = "人事信息"` (或包含空格) 时，后端会检查 `title` 字段：

*   **映射为 "招考招聘"**: 如果标题包含以下关键词之一：
    *   `招聘`, `招考`, `录用`
    *   `遴选`, `公选`
    *   `面试`, `笔试`, `成绩`
*   **映射为 "人事任免"**: 其他情况（默认）。

### 3.2 长度截断
*   任何分类名称超过 255 字符将被自动截断，防止数据库错误。

## 4. 接口对接指南

### 4.1 获取分类列表
前端应在初始化时调用此接口，渲染 Tab 菜单或筛选器。
*   **API**: `GET /api/public-info/category/list`
*   **Response**: `["政策法规", "人事任免", "招考招聘", ...]`

### 4.2 获取分类数据
查询特定分类下的数据。
*   **API**: `GET /api/public-info/category/data`
*   **Param**: `categoryTag=人事任免` (必须使用标准名称)
*   **Param**: `page=1`

## 5. 爬虫开发规范 (Crawler Standards)

为了确保数据的一致性和准确性，爬虫团队需遵循以下规范：

1.  **直接使用标准分类**: 
    *   新开发的爬虫脚本**必须**直接使用标准分类名称（`人事任免` 或 `招考招聘`），严禁继续使用模糊的 `人事信息`。
    *   存量爬虫脚本应在下一次维护周期中进行更新。

2.  **分类判定规则**:
    *   **招考招聘**: 标题包含 `招聘`、`招考`、`录用`、`遴选`、`公选`、`面试`、`笔试`、`成绩` 等关键词。
    *   **人事任免**: 涉及人员职务变动、任免通知等，且不包含上述招聘类关键词。

3.  **数据清洗**:
    *   入库前请去除 `title` 和 `content` 中的多余 HTML 标签和乱码。
    *   确保 `publishTime` 格式正确。

> **注意**: 后端虽然保留了对 `人事信息` 的兼容映射逻辑，但这仅作为过渡方案。长期依赖后端推断会增加维护成本并可能导致分类不准确。
